## 概要

一太郎（JustSystems 一太郎）の文書（JTD / JTT）において、画面上に引かれた**「罫線」**は、Microsoft Word のような入れ子型の表セル（Box モデル：`Document → Table → Row → Cell`）でもなければ、独立した図形・テキストボックス（「レイアウト枠」）でもない。

一太郎において**「罫線」と「枠（レイアウト枠・オブジェクト枠）」は全く異なる概念**である：
* **枠（レイアウト枠・オブジェクト枠）**: 用紙上に配置される独立した矩形オブジェクトであり、別ストリーム（`/LayoutBoxText`、`/LayoutBox`、`/Frame`、あるいは OLE2 サブストレージ）として本文から完全に分離して管理される。
* **罫線**: 本文ストリーム（`/DocumentText`）上に直接引かれ、行グリッドの途中に壁を立ててテキスト流路を分割し、左右の空間（スパン）内で独立して折り返させる**本文レイアウト機構**である。

一太郎にはそもそも「表（Table）」や「セル（Cell）」という独立したデータ構造は存在せず、連続する行に同位置の縦罫線が反復して引かれた結果として、視覚的に「表」が現れる。

本仕様は、この**罫線によって分割された本文テキストストリーム**から、Apache Tika 4.0.0 が要求する表構造（HTML Table：`<table>`, `<tr>`, `<td>`）をリバースエンジニアリングして再合成（Synthesis）するための**流路復元モデル、表状態機械、および XHTML / Markdown 出力契約**を定義・標準化するものである。

v0.3.0 において、流路イベント語彙（`RuleFlowParser`）、平文不変量（テキスト全量保存）、Coalesce（物理セル統合）規則、**`0x000e` による確定的行境界（Row Advance）判定**、**行ヘッダのスパン数算術規則（$w_5 = 4(n-1)+3$）**、**列スロット和集合および `colspan` 近似算出（`RuleFlowAssembler`）**、マルチシート・レイアウト枠のカプセル化、および方位不変性（横書き/縦書き共通挙動）は**実装・確定済み（Accepted / Implemented）**である。様式束文書における複数テーブル自動分割の境界判定や、`rowspan` 近似、特殊な文脈語義については、将来課題（Phase 3+）として管理する。

## 1. 設計思想とメンタルモデル（流路 Doctrine）

### 1.1 Box モデル vs ストリーム分割モデル

| 概念 | Word / HTML（Box モデル） | 一太郎の「罫線」（ストリーム分割モデル） |
| :--- | :--- | :--- |
| **基本単位** | セル（Box）。箱が先に存在し、テキストが収まる | 行グリッド（流路）。テキストストリームが主体 |
| **縦罫線の役割** | セルの境界線を定義する属性 | 流路の指定座標に「壁」を立て、左右で独立に折り返させる |
| **セル内折返し** | セル内部の通常改行 / 段落 | 次の表示行（display 行）へ進み、同一スパンへの再宣言が発生 |
| **横罫線の役割** | 行（Row）の境界線を定義する属性 | 水平方向の区切りイベント（または流路の仕切り） |
| **表の存在** | `<table>` という明確なコンテナオブジェクト | 連続する行に同位置の壁が反復して立った結果生じる「視覚的グリッド」 |

### 1.2 パーサーの役割の再定義

> **本パーサーの役割は「一太郎の表構造をパースすること」ではない。**
> **罫線で切り刻まれたテキストストリームから、失われた高次構造（HTML Table）をリバースエンジニアリングして再合成（Synthesis）することである。**

パーサーは、ストリーム上に現れる断片的なスパン宣言や境界イベントを監視し、同一物理スパンの統合と反復グリッドの検出を通じて、DOM ツリーとしての `<table>` / `<tr>` / `<td>` を能動的に組み立てる。

## 2. 流路イベント語彙とバイナリ不変量

`/DocumentText`（RFC 0003）のトークンストリームにおける各制御コードおよびレコードは、以下の流路イベントとして抽象化される。

### 2.1 流路イベント体系

| コード / レコード | 流路概念（RFC 0013 語彙） | バイナリ特性 | SAX / XHTML 射影 |
| :--- | :--- | :--- | :--- |
| `0x001c` (class `0x0030`) | **Span Reaffirm**（スパン再宣言） | 12語固定ヘッダ。スパン左辺 $b_0$・右辺 $b_1$ を保持。同一行内の $b_0$ ジャンプがスパン遷移を表す | `<td>`（Coalesce 単位） |
| `0x000e` | **Row Advance**（行境界・行前進） | ペイロードなし区切りコード。**行末に必ず 1 個出現**し、行内のスパン遷移では出現しない | `</tr>`（行境界確定） |
| `0x000a` | **Stream Wrap**（流路内折返し） | ペイロードなしコード。スパン内折返し、またはスパン境界。本文テキストのない罫線行ではスパン宣言の直後にスパン間前進マーカー（Blank Wrap）としても出現する（交差罫線統制サンプル） | `<br>` 候補。Blank Wrap は emit しない |
| `0x001c` (class `0x0010`) | **Line Header**（行ヘッダ） | `w4=0x008f`: 列仕様ヘッダ（スパン数 $n$、スタイル符号、壁 tag） / `w4=0x0020` 等: 段落整形 | `<tr>` 新行開始、または `<p>` |
| `0x001c` (class `0x0020`) | **Flow Terminate**（流路終端） | 表→段落の明示的遷移 | `</table>` close |
| `0x000c` | **Terminator / Structural Word**（終端／構造語） | 独立したページ切れとしての出現は未確認：観測された `0x000c` 語は、セルレコードの長さフィールド（len=12）、埋め込み表組構造語、および stride-2 列挙表（整数 1..N を 2 語 pitch で格納した索引表。旧観測の終端記述子はこれの誤読）に分解される | (none for v1; reserved) |

### 2.2 平文不変量（Plain Text Invariant）
 
本仕様に基づく構造化 SAX 出力の導入にあたり、以下の平文不変量を最優先制約として保証する。
 
* **実質文字全量保存則**: 構造化処理によって emit される文字列、および `-t` 高速パス（直接平文抽出）の出力文字列は、構造化前の実質テキスト内容（日本語・全角・英数記号）を完全に保存しなければならない。
  - なお、XHTML シリアライザ（`ToXMLContentHandler` / `ToMarkdownContentHandler`）による整形改行・タグ境界インデントの挿入に伴い、`-t` の平坦化出力は v0.2.x 以前の生バイナリ抽出と完全バイト一致から「全空白除去正規化において完全一致（CJK・全角欠落ゼロ）」の保存則へ移行した。
* **混在型（P1）前置きテキスト保存**: TextV.01 span の最初のマーカー手前にテキストが存在する場合（混在型前置き）、これを先頭の `Text` イベントとして欠落なく復元する。
* **文字順序保証**: スパン分割されたテキストは、ストリームに出現する自然な順序（物理行・スパン進行方向）に従って連結され、文字の欠落や重複を生じさせてはならない。
* **バイナリグリフ・制御域ノイズの排除**: 旧パーサーで緩い run 開始規則により混入していた制御域（`0x00`〜`0x1f`、`0x001c` 自身など）や Latin-1 由来のバイナリ残骸グリフ（`´`, `¨`, `¤` 等）は、構造化出力には含めず除外する。
* **自動採番接頭辞の復元**: 箇条書き・丸数字などの自動採番接頭辞は、平文契約と同一の規則（`paragraphHeaderPrefix`）で本文ストリームへ復元する。

### 2.3 方位不変性（Orientation Invariance）

* 一太郎の座標系および流路イベントは、本文進行方向に対する相対空間（Orientation Relative Space）で統一されている。
* 縦書き文書においても、行ヘッダスタイル符号（`0x08`, `0x14`, `0x13`）、Reaffirm（毎行宣言）、スパン間隔（gap=2）、および行境界（`0x000e`）は**横書きと全く同一の値・同一挙動**を示す。
* **見た目は書字方向ではない（照合標本の教訓・所有者確認済み）**: 照合標本（実文書）は横書き設定の文書であり、縦書きに見えるのは一文字幅の囲み空間で一文字ずつ改行して作られた見せ方である（囲み空間幅ヒストグラム: $20$ 単位＝一字幅×377 個が支配的）。パーサーは書字方向を目視的外観から推定してはならず、外観だけで `jtd-vertical` を付与してはならない。書字方向は PaperMark の方向グループ（§2.5）／RFC 0007 から取得する。
* **罫線は進行終端側で開く（所有者確認済み）**: 罫線はボックスではないため、自由端を開いたままにできる——横書きなら下端、縦書きなら左端。両者は一つの法則に統合される: **開く端＝進行方向の終端（exit）**（横書きなら下、縦書きなら左＝進行軸の末尾側）。BOX 文法ではこれは閉行宣言（`0x15`）の単なる欠落に対応し、閉じた輪郭は明示的な閉行を要する。

### 2.4 スパン軸の確定（Confirmed）

* スパンヘッダのスパン座標 $b_0$ / $b_1$ は**advance 軸（テキスト流路軸・書字方向に対する相対軸）**上の座標であり、用紙幅軸の座標**ではない**。
* 流路を横断する罫線（例：縦書き文書の横罫）は、advance 軸上の交差座標に壁として符号化され、**交差する advance 単位ごとに再宣言（Reaffirm）される**。再宣言回数＝交差回数（交差罫線統制サンプルで検証：36 件の行ヘッダ `w4=0x008f`、各行でスパンが `[0,40]→[42,160]` に分割、壁 tag `0x0028`=40、PDF 出力上の罫線位置は本文領域の 41/160 にサブミリ精度のマージン誤差内で一致）。
* **ギャップの大きさは、交差域における文書固有のテキスト振る舞いを符号化する**（本文テキストが存在しない純罫線文書では幅 1 単位の壁、テキストが罫線を避ける場合は広い回避空白、照合標本で観測され交差罫線統制サンプルで実証されたように、テキストが罫線上下の両スパンに載って跨ぎ span として現れる場合もある）。ギャップの寸法は罫線の物理的な長さではない。
* **流路グリッドイベントは本文テキストに依存しない**：本文のない空のページに罫線 1 本を引くだけでも reaffirm ×36 ＋ WALL 列が emit される（本文なし交差罫線統制サンプルで検証：本文テキストゼロ、`/Header` のフッターのみ）。
* **イベント計数のプロトコル**: `/DocumentText` の素走査では、`SsmgV.01` ストリームヘッダ（先頭 16 語）と埋め込み stride-2 列挙表を除外しなければならない。それらの値（`0x000a`/`0x000c`/`0x000e`）は WRAP/BREAK/WALL イベントに化けるためである。ヘッダ偏移 9 語の値はサンプル改版により変動する（本文ブロック追加で 13→14）——RFC 0003 の decoded 化候補（セグメント／領域数フィールド）として登記。

### 2.5 PaperMark の方向グループ（統制サンプル 6 件で検証）

`/PaperMark` は `[0][N][0][0x000c][0][N-1]` に続き N 個のグループ `(0x0000, idx, 0x0001, orient)` が並ぶ:

| サンプル | 書字方向（所有者確認） | orient（idx 別） |
| :--- | :--- | :--- |
| 統制サンプル（横書き） | 横書き | idx0=`0x10`・他 `0x0000` |
| 統制サンプル（長罫・横書き） | 横書き | idx0=`0x10`・他 `0x0000` |
| 照合標本（横書き設定・縦見せ） | 横書き（縦見せ） | idx0=`0x10`・他 `0x0000` |
| 統制サンプル（縦書き） | 縦書き | idx0..idx2=`0x10`・他 `0x0000` |
| 統制サンプル（縦書き・交差罫） | 縦書き | idx0..idx2=`0x10`・他 `0x0000` |
| 統制サンプル（縦書き・交差罫・跨ぎテキスト） | 縦書き | idx0..idx2=`0x10`・他 `0x0000` |

* **判別則（6/6 検証）**: idx ≥ 1 のいずれかのグループが `orient=0x10` を持つ ⟺ 縦書き。
* idx0 は横書きサンプルでも `0x10` を持つ——idx0 の対象物は不明（RFC 0007 で解読・予約）。
* 語彙注記: 本仕様で「セル」と呼ぶものは、一太郎の概念では**交差する罫線が作る囲み空間**（縦 2 本×横 2 本等）であり、一太郎にセルというオブジェクトは存在しない（所有者確認済み）。

## 3. 表状態機械（Table State Machine v2）仕様

パーサーは、以下のステップからなる状態機械によって表構造を検出・正規化する。

### 3.1 行ヘッダによる列数算術（Column Count Arithmetic）

* 行ヘッダ `w4=0x008f` のペイロード先頭語 $w_5$ は、当該行の物理スパン数 $n$ に対して以下の厳密な算術を満たす：
  $$w_5 = 4 \times (n - 1) + 3$$
* これにより、パーサーは行の開始時点で当該行の期待スパン数 $n$ を事前に確定できる（$w_5=7 \Rightarrow n=2$、$w_5=11 \Rightarrow n=3$、$w_5=15 \Rightarrow n=4$）。

### 3.2 同一スパン統合（Coalesce）規則

* **背景**: セル内でテキストが複数行に折り返されるたびに、表示行単位で同一座標 $[b_0, b_1]$ を持つ `0x0030`（Span Reaffirm）が反復 emit される（Word における `\intbl` 行に相当）。
* **規則**: 同一の行（または連続するスパン区間）において、同一の境界座標 $[b_0, b_1]$ を持つ連続する `0x0030` レコードは、**同一の物理セル（単一の `<td>`）として統合（Coalesce）**する。
* **効果**: セル内改行や折返しによる列数の異常肥大化を防ぎ、物理的なセル単位へ収束させる。
* **リグレッション・アンカー（正解 HTML 照合標本・登記済み）**: Span Reaffirm 844→物理セル 128＝**6.59 倍**、行前進 59→論理行（`<tr>`）9＝**6.56 倍**。二つの係数が一致することから、**coalesce 収束定数＝セルあたりの display 行数（この標本で約 6.5 行）**と実測裏付けされる。構造リグレッションは正解 HTML に対し tr/td/colspan/rowspan 骨格の形状照合のみで行う（本文非開示）。

### 3.3 境界ストリップとスパン間隔

* 隣接スパン間の間隔（$b_0' - b_1$）は通常 $2$（または $4$）であり、これは罫線自身の占有幅に対応する。
* **空の境界ストリップ除外規則**: スパン幅が極小（$b_1 - b_0 \le 4$ 単位）**かつテキストを含まない（空である）** レコードのみを境界ストリップ（遊び）として扱い、コンテンツセルから除外する。テキストを保持している狭幅セル（申請書等の幅 4 一文字マスなど）はコンテンツセルとして確実に保持する。

### 3.4 確定的行境界（Row Advance）

* **規則**: `0x000e` が出現した時点で、**現在の行（`<tr>`）を確定的に終了**する。同一行内のスパン移動時に `0x000e` が出現することはなく、`0x0030` の $b_0$ 座標の変化によってのみ次のセルへ遷移する。

### 3.5 表開始（Table Open）判定

表の開始は、以下のいずれかの条件を満たしたときにトリガされる。

1. **安定グリッドの反復（主シグナル）**:
   Coalesce 後の物理スパン数が $n \ge 2$ であり、かつ連続する行間でスパンの開始座標列（left 座標列）が一致する「安定グリッド」が検出された場合。
2. **表行ヘッダの出現（補強シグナル）**:
   `0x001c` (class `0x0010`, `w4=0x008f`) の列仕様ヘッダが出現した場合。

#### 誤検出（False Positive）防止ガード
* 単一カラム段落（$n=1$）では表を開かない。
* `0x000e` 単独（`0x0030` の安定対応がない場合）では表を開かない（水平罫や折返し装飾の残骸を除外）。
* 非表の装飾枠（破線シール枠等）は、Coalesce 後のスパン数が閾値未満となるため表として認識しない。

### 3.6 列スロット和集合の導出と正規化・`colspan` 近似

表状態機械（`RuleFlowAssembler`）は、表開始から終了（Table Close）まで行群をバッファリングし、全行の情報を統合して出力する。

1. **列スロット（Column Slots）の確定**:
   表内のすべての行に含まれる各セルの開始左辺座標（$b_0$ 列）の和集合（Union）を昇順にソートし、表全体の統一グリッドスロット（列槽）を確定する。
2. **欠落スロットの空セル補完**:
   各行において、統一グリッドスロットに対応するセルが存在しない位置（欠落スロット）には空の `<td/>` を自動補完し、不整形表による Markdown（GFM パイプ表）のレンダリング崩れを防止する。
3. **`colspan` 近似属性の算出**:
   セルの右辺座標 $b_1$ が後続の列スロットを跨いでいる（幅広セルである）場合、包含するスロット数 $k$ を算出して `colspan="k"` 属性を付与する。この属性は XHTML 出力で保持され、Markdown（GFM）出力では表平坦化により透過される。
4. **`rowspan` について**:
   同一列槽における複数行のセル結合（`rowspan`）は、v0.3.0 時点では行境界（`0x000e`）による確定的 `<tr>` 区切りを優先し、将来課題（Phase 4+）として追跡する。

### 3.7 表終了（Table Close）判定

以下のいずれかのイベントが発生したとき、直ちに現在の `<tr>` および `<table>` を閉じる。

1. `class 0x0020`（Flow Terminate / 表→段落遷移）の出現
2. 表属性を持たない通常段落ヘッダ（class `0x0010`、単一カラム）の出現
3. 安定グリッドから外れた通常テキストランの出現
4. ドキュメントストリームの終端（EOS）

### 3.8 罫線はページを跨がない（所有者確認済み）

* 一太郎の罫線は**1 ページ以内に引かれ**、物理的に次ページへは継続しない。罫線は開いた端を持つストローク（ボックスではない）であるため、自由端は開いたままでよい——横書きなら下端、縦書きなら左端（§2.3）。
* 「ページを跨いで見える表」は**視覚的な継続**である。N ページ目は進行終端側を開いて罫線を終え、N+1 ページ目は進入側（受け口）を開いた新たな罫線を引く。両ページのグリッドは、たまたま揃った独立のストロークである。
* **状態機械の帰結（新たな終了信号）**：すべてのページ境界は強制的な table close である。安定グリッドをページ境界またぎで単一の `<table>` として継続させてはならず、各ページが各々 `<table>` を開く。連続ページは consumer 側のヒント（`data-table-run="k"`）で紐づけうるが、DOM の table はページ単位である。
* これは様式束標本（9 ページ反復グリッド）を決着させる：9 ページに反復する `lefts=[4,16,24,…]` グリッドは同一様式の 9 回の独立再描画であり、1 つの跨ページ表**ではない**。各「様式第ｎ号」ページが自らの表を閉じる。
* これは単一表の照合標本も再定義する：罫線はページ跨ぎしないため、前述の「跨ページ tbody」射影は不要であり、各ページが自己完結した表である。
* **検出への帰結（RFC 0003/0007 へ登記）**：`/DocumentText` 内のページ境界信号は、座標の再開／ストリームヘッダのセグメント数（偏移 9 語——文本ブロック追加で増加）および PageMark から取るものとし、専用のインフロー改ページコードからは取らない（standalone `0x000c` は LEN 語／stride-2 列挙表へ分解される——§2.1）。権威ある改ページトリガの所在特定がデコード対象である。

## 4. 罫線スタイル符号体系（本文側ヘッダ構造）

罫線の描画スタイル（太さ、色、線種、行内/行間）は、別ストリームではなく、**本文側行ヘッダ（`0x001c` class `0x0010`）内に直接符号化**されている。

### 4.1 フロー分割型と行間型

* **`payload[4] == 0x14`（行内横罫）**: テキスト流路を横方向に分割する。罫線そのものはスパンの隙間（gap）として座標復元可能である。
* **`payload[4] == 0x08`（行間横罫）**: フローを分割せず、全幅スパン（$[0, 160]$ 等）を維持する。
* **BOX 境界文法**: 外枠（BOX）は、**開行（`0x16`） $\rightarrow$ 中段（`0x13` $\times N$） $\rightarrow$ 閉行（`0x15`）** の三部構成で流路を包囲する。中段の `0x13` サブブロック内の tag 値が縦壁の $x$ 座標を表す。
* **交差罫ランプ（Crossing Rule Ramp）**: 複数の advance 単位にまたがる罫線は、スタイルワード内で **先頭単位（`0x12`） $\rightarrow$ 中間単位（`0x13` $\times N$） $\rightarrow$ 末尾単位（`0x11`）** を宣言する。BOX の開行／中段／閉行（`0x16`/`0x13`/`0x15`）と同じ文法族である。

### 4.2 罫線スタイル（末尾語）と tag 座標

* **縦壁 tag**: 列仕様サブエントリ内の tag 値（例: `0x4e = 78`）は、縦罫線が引かれた壁の $x$ 座標そのものを表す（例: $b_1=78 \mid b_0=80$）。
* **ヘッダ末尾語**: 罫線の描画属性を示す。
  * `0x22`: 細線・黒
  * `0x1c`: 太線・黒
  * `0x06`: シアン・破線
  * `0x4f`: 縦罫・細黒
  * `0x00`: 孤立罫（standalone）

## 5. 出力射影仕様（XHTML & Markdown Dual Contract）

パーサーが emit する SAX イベントは、Apache Tika 4.0.0 の ContentHandler パイプラインを通じて、XHTML と Markdown の双方に正しく射影されなければならない。

### 5.1 エンドポイントとハンドラの二重契約

| 出力形式 | Tika 4 エンドポイント | パーサー側の責務 | シリアライザ側の挙動 |
| :--- | :--- | :--- | :--- |
| **XHTML** | `PUT /tika/xml` | 完全な XHTML 構造（`<table>`, `<tr>`, `<td>`, `<tbody>` 等）を emit | 属性（`class`, `data-rule`, `rowspan`, `colspan` 等）を保持して XML 出力 |
| **Markdown** | `PUT /tika`（既定） | 同上（XHTML ハンドラへ emit） | `ToMarkdownContentHandler`（commonmark-ext-gfm-tables）が GFM 表に自動変換 |
| **Plain Text** | `PUT /tika/text` | 同上（または `-t` 高速パス） | 全タグを除去し、テキストノードを改行区切りで結合 |

### 5.2 GFM パイプ表の制約とフォールバック

Tika 4.0.0 の `ToMarkdownContentHandler` は commonmark-ext-gfm-tables 0.30.0 に依存しており、以下の制約が存在する。

1. **先頭行のヘッダ扱い**: 最初の `<tr>` が自動的に `TableHead`（ヘッダ行＋`|---|` 区切り線）となり、以降の行が `TableBody` となる。
2. **Colspan / Rowspan の非対応**: GFM 表仕様には結合セルが存在しないため、属性は無視されセルは平坦化される。
3. **入れ子表の深度制限**: 入れ子表は `tableDepth == 1`（最外側）のみが表としてレンダリングされ、内側の表は平坦化される。パーサー側は入れ子表を検出した場合、必要に応じて `<div class="nested-table">` 等のカプセル化を行う。

### 5.3 書字方向（縦書き）の射影

* 縦書き文書における表は、相対空間のまま `<table>` に射影し、`<table class="jtd-vertical">` 属性を付与して出力する。視覚的な転置（行と列の入れ替え）は消費側の責務に委ねる。
* **消費者契約の作例（ground truth として登記済み）**: 照合標本原本（横書き設定・一文字改行による縦見せ文書——所有者確認済み）を所有者が手作業で HTML 再現した作例は、単一表（`tr` 9・`td` 128・colspan 54・rowspan 17・`th` 65・`tbody`×1、`dir`/`writing-mode` の指定なし）である。これはパーサーが流路構造を忠実に出力し、書字方向は PaperMark からのみ取得する（外観からは取得しない）という設計分業の実証である。span 情報 71 件は Markdown 側では平坦化により欠落し、§5.2 の予測どおりとなる。

### 5.4 文書構造・マルチシート・枠の封じ込め契約（v0.3.0 実装確定）

Apache Tika 4 の SAX 出力パイプライン（`XHTMLContentHandler`）との統合において、以下のカプセル化契約を確立する。

1. **マルチシート文書のカプセル化**:
   - シートごとに `<div class="sheet">` 要素で区切り、先頭に `<h2>{シート名}</h2>` を出力する。
   - シート内の本文、表構造、およびシート毎脚注（`<p>{脚注}</p>`）をその内部に包含する。
   - シート間およびシート内の連結順序契約は不変である。
2. **レイアウト枠（`/LayoutBoxText`）の封じ込め**:
   - テキストボックスとしてのレイアウト枠は、文書末尾において「※枠内テキスト」テキストノードに続き、`<div class="layout-box">` 要素でカプセル化して出力する。
   - 枠内の各ブロックは独立した段落 `<p>` として構造化する（`-t` 平文互換性維持）。
3. **二重 `<body>` 要素の排除**:
   - `XHTMLContentHandler` は `startDocument()` / `endDocument()` に連動して自動的に最外層の `<body>` を開始・終了する。パーサー側で明示的な `<body>` タグを発行せず、Tika 本体の妥当な XHTML 生成に委ねる。
4. **破損コンテナのサルベージ分割処理**:
   - 不完全・破損した CFB コンテナから救出された生ストリームにおいて、複数断片が `[0x00, 0x00]` で連結されている場合、語アラインメントを保ったマジック走査により断片単位へ分割し、各断片を個別に流路構造化してテキストを回収する。
5. **フォールバック保証**:
   - 流路構造化またはシート情報の解読で予期せぬ例外が発生した場合は、ストリーム全体の文字全量を維持するため、従来の平文 1 ノード出力へ安全にフォールバックする。

## 6. 概念の境界：レイアウト枠との峻別と接続

本仕様は「罫線による表」を中核とし、**「レイアウト枠（LayoutBox）」とは明確に区別**される。

1. **ストリームとライフサイクルの相違**:

## 13. 縦継続セルと前置きテキスト（2026-09-30 観測・Phase 2 準拠の追補確定）

月历（年間行事予定）型・記入欄グリッド型の実文書で確定した 2 契約を、§3 表状態機械・§5 出力射影の**上書きでない限定条項**として登記する。既存の §3.4 確定的行境界・§5.4 / §12.4 T3-1（セル内改行の半角スペース平坦化）は、本節が列挙する場合以外では完全に維持される。

### 13.1 TextV.01 名なし前置き本文の復元（欠落防止）

* `/DocumentText` には、`SsmgV.01` ヘッダ直後のセグメント名が `TextV.01` ではなく、ヘッダ語 10 杯から最初の RFC 0009 マーカー（`0x001c` / `0x001d` / `0x001f`）の手前までが raw な UTF-16BE 本文（表題行など）になっている型が存在する。
* この型の文書では、当該領域をストリームの先頭 [FlowEvent.Text] として復元する（表より前に `<p>`）。これにより文書冒頭・表外の表題行が丸ごと欠落しなくなる。
* リグレッションガード:
  * `TextV.01` 名あり文書（§混在型 P1）は既存 [rawPrologueText] が担い、本節は発火しない（排他）。
  * 走査域に空白以外の可視テキスト語（CJK / 全角 / ASCII printable。§3 の可視語判定に同一）が 1 つもない場合は前置きを作らない。
  * 域内の未観測語（可視語規則外・`0xFE00`〜`0xFE0F`）が 1 つでもあれば前置き全体を採用しない（誤デコードでゴミを混ぜない）。
  * マーカーが語 10 未満（先頭から構造レコードが始まる従来型フィクスチャ）は発火しない。
  * CR / LF は本文終端として扱って打ち切る（当該折返しは本体走査側の [FlowEvent.Wrap] に委ね、二重 emit しない）。

### 13.2 縦継続セル（tall cell）の論理行統合と [FlowPart.LineBreak]

月历型の行では、論理的に**縦に長い 1 セル**が `WALL(0x000e)` で分離された複数テキスト行へ折返って現れる。これを 1 論理行 `<tr>` へ統合する契約をここで確定する。

* **統合条件**（すべてを満たす物理行対 $A$(先行) / $B$(後続) のみ）:
  1. $A$ のコンテンツセル（境界ストリップ除外後）に、生 parts がセル末尾でセル内 WRAP（[FlowEvent.Wrap] 由来の [FlowPart.Break]）を終端とする非空白セルが 1 つ以上ある（先行行が次テキスト行へ折返るシグナル）。
  2. $B$ の生宣言スパン列（境界ストリップ filter 前の全セル）が $A$ と同一の署名（$(b_0,b_1)$ の順序列）である。
  3. $A$・$B$ とも**各自の RowHeader**（`0x001c/0x0010` `w4=0x008f`）を宣言している。ヘッダを共有して連なるヘッダなし WALL 行（§12.3）は§3.4 の独立 `<tr>` を維持し、統合しない。
  4. 3 行以上の連鎖は、各継ぎ目で同上を満す限り開いたまま連結する。統合後は $B$ の折返しシグナルで継続可否を更新する。
* **射影**: 統合セルの継ぎ目は [FlowPart.LineBreak] に射影し、XHTML では `<br/>` を emit する。[FlowPart.Break]（同一セル内の折返し）の半角スペース平坦化（§12.4 T3-1 / §5.4）は継ぎ目でも不変（[FlowPart.LineBreak] と [FlowPart.Break] は別語彙）。
  * 例: `|１<br/>月|新入生テスト|開校記念日 <br/>魚沼実踏①|...|`（1 論理行）。
* **空後続セル**: $B$ の対応セルが空白なら継ぎ目を置かず、$A$ の parts をそのまま残す（両方空白なら空 `<td></td>`）。
* **境界ストリップ**: 統合判定・マージは filter 前の全セルで行い、$b_1-b_0 \le 4$ の空白ストリップ除外は論理行を `tableRows` へ flush する時点で適用する。月历実文では末尾ストリップに `··` 様の空白文本が乗る行と空行が交互に来るため、filter 後の署名で判定すると同一論理行が別署名化して統合が破綻する（§13.2 の所以）。
* **`rowspan` 近似（§3.6 / §12.4 T3-3）**: 統合で論理行数が物理行数より減るため、§3.6 の列槽計算・`rowspan` 近似は**統合後の論理行**を単位として導出する。
* **Markdown**（§5.2 / §5.4）: 統合セルの [FlowPart.LineBreak] は XHTML で `<br/>` だが、Tika 本体の `ToMarkdownContentHandler` に渡すとハードブレーク（`  \n`）へ変換されるため、T3-1 と同一の主因で GFM 表行を断片化させる。パーサーは本節で `<br/>` を増やさず、断片化の回避は §5.2 のフォールバック・§7.2 に委ねる（追跡項）。

### 13.3 トレース・受入

* 文書骨格フィンガープリント（`tr` 数・セル内 `<br/>` 出現・先頭段落）で照合するオプトインレール（`-Ptallrow.rail`）で、§13.1 の先頭段落復元と §13.2 の縦統合（`br-in-td > 0`）を骨格数値で固定する。
* 上記文書の `-t` 出力の差分は、本文の全除去正規化で先行内容を順序保存した上位集合であること（テキスト全量保存則 §2.2）と、非可視グリフの欠落ゼロを HEAD 比較で確認済み。

## 14. 録図グリッド構造の折込と継続（2026-09-30 観測・追補確定）

本節は、§3 の行・セル状態機械、§5 の出力射影、および §13.2 の縦継続統合を限定・補強する 5 契約を登記する。列槽和集合、本文保存、および確定的な WALL 境界を維持する。

### 14.1 偽インライン拒否の限定（R1）

* RFC 0009 レコード検証における本体の `0x001d` 拒否は、その直後が `0x001e`（インライン区間閉じ）である場合に限る。`0x001d` 単独は、列領域語（w5）等の正当座標語と同値になり得る。
* 行間区切りヘッダの実測形（len=`0x0029`、w5=`0x001d`）はこの規則で承認される。旧ガードは当該ヘッダを誤拒否し、レコード拒否後に露出した len 語 `0x0029`（`)`）を本文へ漏らして表を物理行ごとに分断し、§9.8 の保存則を破っていた。
* `0x001d`〜`0x002a` の連番制御語列に対する誤検出ガードは、本限定後も維持する。

### 14.2 縦継続統合の収縮（R2）

* §13.2 の同一スパン署名・行ヘッダ等の統合条件に加え、後続物理行が語6=`0x0001`（完結セル）であり、先行論理行の閉じた（非空白かつ WRAP なし）テキストセルと同一スパンに新しいテキストを宣言する場合は統合しない。§3.4 の確定的行境界を優先し、別の `<tr>` とする。
* 語6=`0x00ff` / `0x0000` の継続・断片宣言による折返し、および空セルからテキストセルへの書き込みは、§13.2 の統合を維持する。

### 14.3 孤立罫断片の折込（R3）

* 空白で幅が 8 以下のスパンが、他行のより広い宣言スパンに真包含される場合、連続する断片 run を包含スパンの空セル 1 個へ折り込む。孤立罫（§4.2 の末尾語 `0x00` 系）がセルを分割すると、流路上は割れ目の両側に断片スパンが宣言されても実体は 1 セルである。
* 折込により §3.6 の列槽和集合を汚染する偽の列境界・`colspan` を除去する。テキストを伴う断片は折り込まず、§2.2 の保存則を優先する。

### 14.4 下方継続アンカー（R4）

* セルヘッダ語7=`0x0002` は、直下の WALL 行へ同一スパンが継続するアンカー宣言である。
* アンカーセルの直下 WALL 行にある非空白セルが、アンカーと同一スパンのものだけである場合、そのテキストを [FlowPart.LineBreak]（`<br/>`）でアンカーセルへ吸収し、断片行を独立 `<tr>` にしない。異なるスパンの非空白セルがある場合は両行を維持する。

### 14.5 ブロック列の rowspan 合体（R5）

* 先頭スパンが空白かつ WRAP 末尾の行を縦長セル群のブロック先頭とする。同一スパンの後続宣言を、次のブロック先頭（同一スパンの空白+WRAP 再宣言）、閉じた非空白テキストセル、またはスパン宣言の欠落まで窓として走査する。窓内に 1 つ以上のテキスト断片がある場合、先頭セルへテキストを集め、`colspan` は列槽から算出し `rowspan` は窓長とする。断片間は [FlowPart.LineBreak]（`<br/>`）で接続する。窓内で罫箱のみを表す空白セルも折込対象から除去する。
* テキストを巻き上げるブロック列は狭幅 column（スパン幅 ≤ 16 単位。実測の縦長 label 枠が一文字幅に折返る系）に限る。広幅 column の各行は独立 box として本文 run を各行に残し、空白スパンの `colspan`×`rowspan` rule のみ適用する（§2.2 順序保存則の担保）。
* ブロック内の空白広幅セルについて、窓の全行に同一スパンがあり、表内の他行にその内部境界となる縦壁座標が宣言される場合に限り、空白の単一セルへ `colspan` と `rowspan` を併せて付与する。

### 14.6 射影と受入

* §13.2 と同じく、統合の継ぎ目は [FlowPart.LineBreak] とし、XHTML では `<br/>` に射影する。§12.5 の T3-1「セル内 br ゼロ」は本節の登記済み継ぎ目を許容する契約へ更新し、2026-09-30 の再登記値を `br-in-td=6` とする。
* Markdown 側の断片シグナル（末尾 2 空白で終端するパイプ行）も同じ継ぎ目に由来する分を許容し、2026-09-30 の再登記値を 5 とする（§5.2・§7.2 追跡項）。
* 合成契約テストは `RuleFlowBlockColumnStructuringTest`（『銀河鉄道の夜』のフィクスチャ）に登記する。text golden は `captureGolden` で再採取済みで、修正前パーサー（HEAD）との横断監査（604 件）の分類は、完全一致 432・空白正規化一致 77・同一文字多重集合（§13.2/§14 の継ぎ目・先頭アンカー合体由来の読み順変更）23・構造語露出の除去 72（HEAD が偽インライン誤拒否で本文へ漏らしていた len 語等の ASCII のみ消滅し、和字本文の欠落はゼロ）・旧採取無し 2 である。順序変動は §13.2/§14 の rowspan 投射に内在する先頭行集中であり、正解 HTML の骨格と整合する。

## 15. pending 表頭部の取り込みと字下げ折返し継続（2026-10-01 観測・追補確定）

本節は §3.5 の表 open、§13.2 の縦継続統合、および §14 R2 の衝突判定を補強する 3 契約を登記する。PDF グリッドオラクル（`tools/pdf_grid_oracle/`。一太郎印刷 PDF の罫線ベクトルからセルグリッド正解を再構築する開発ハーネス）による突合で観測・確定した。

### 15.1 表 open 時の pending 取り込み（refinement 許容）

* 表 open が行ヘッダ補強（w4=`0x008f`）で決着する場合、pending に待避済みの multi-span 行（行ヘッダ無しの表頭行が該当）について、そのスパン左辺座標集合が open 行の左辺座標集合と一致、**または一方が他方の部分集合（列の細分化 refinement）**ならば、pending を表の先頭行（複数行の場合は全行）として取り込む。
* refinement は点線（うす罫）相当の列が本文行側だけで細分される実版面に頻出する（表頭行は細分前の span を跨いで宣言され、`colspan` 近似として射影される）。§15.2 と併せて、ヘッダ行が段落へ転落する欠陥を解消する。
* 交差・無関係グリッドの pending は従来どおり段落へ退避し、§2.2 の保存則を維持する。

### 15.2 空区切り行による pending 消滅の禁止

* `content` が空のセグメント（WALL 重複・分節罫のみを行）は、表 open 前の pending を消滅させてはならない。pending は後続の表 open と接続されるまで保持し、段落退避が必要になるのは EOS の放棄（§3.7）で保証される。
* 表 open 前に空区切り行を挟む版面（表題行 → 空区切り → 本文行）で、表頭行が段落へ放棄されていた欠陥を解消する。

### 15.3 字下げ折返し継続の吸収（B）

* WRAP 語（`0x000a`）を伴わず WALL 分割だけで折返す版面では §13.2 の WRAP 終端シグナルが不発となる。この種の版面で一太郎は折返し継続テキストの先頭に全角スペースの行頭字下げを付す。
* 同一表コンテキスト内で、行ヘッダを持ち open 行のスパン署名が先行論理行の部分集合以上の対応を持つ断片行について、その**全非空テキストセルが行頭空白類で始まり、かつ同一スパンの先行セルが非空**である場合（1 セル以上の該当が必要）、断片行を先行論理行へ [FlowPart.LineBreak]（`<br/>`）で吸収し、独立 `<tr>` としない。
* ガード: 字下げのない新テキスト、未宣言スパンの非空セル、先行側が空のセルが 1 つでもある行は吸収しない（新論理行として flush）。§14 R2 の完結セル衝突判定はスパン単位マッチへ更新し、署名一致・refinement 一致のいずれでも同一結果となることをもって既存挙動の不変を担保する。

### 15.4 射影と受入

* 継ぎ目は §13.2/§14.6 と同じく [FlowPart.LineBreak] → `<br/>` に射影する。
* 合成契約テストは `RuleFlowPendingHeaderRowAdoptionTest`（取り込み 3 契約）と `RuleFlowTallRowContinuationTest`（refinement 吸収・字下げ吸収）に登記する（『銀河鉄道の夜』フィクスチャ）。
* 実コーパス 604 件の text golden 横断監査（追補適用前後）: 完全一致 464・空白正規化一致 83・純順序差 57・**和字含め文字欠落ゼロ**・exit 反転ゼロ。順序差は断片テキストが物理レイアウト上の正しい位置へ移動するものであり、PDF オラクルで裁定済み（字下げ継続セルの観測と一致）。vertical・keisen・jttc 系は差分ゼロ。

## 16. 縦書き band の SPAN 木グリッド再構成（2026-10-01 観測・追補確定）

本節は §3.4 の WALL 行境界と §13.2 の縦継続統合を補完し、時間割等の縦書き連続領域（band）を可視行グリッドへ復元する契約を登記する。PDF グリッドオラクルの水平罫ジオメトリ（band 内部罫の x 範囲）とバイト列の open/close 周期との対応で観測・確定した。

### 16.1 band の検出・バッファリング・終端

* 行ヘッダ（`w4=0x008f`）を伴わず、WRAP 終端（語 `0x000a`）マスを 1 つ以上含む行は縦書き band の物理行である。表コンテキストでは flush せず band バッファへ預ける。
* 表 open 前（pending 段階）に WRAP-open 行が現れ安定グリッド取り込み（§3.5・§15）で表が開く場合、その行を開き頭の band として開始し、取り込まれた pending の中にも WRAP-open 行があれば band へ移す。band 宣言行が素の `<tr>` として残る誤射印を解消する。
* band 終端は WRAP-open マスが 1 つもない行（空区切り行・閉じた集計行を含む）、行ヘッダを伴う行、または表 commit とする。本文が空白でも WRAP-open マスが残る行は縦流れの埋め立て（マスが下方向に開いた継続）であり、終端としない。

### 16.2 空区切り行の幽霊行禁止

* 全マスが空白の行は表コンテキスト内で `<tr>` を立てない（flush のみ）。テキストを運ばないため保存則 §2.2 に触れない。開いていた論理行は確定する。

### 16.3 可視行境界（開→本文→閉→欠落→再開）

* 可視行番号を進める境界は 2 種とする。
  - (a) 再開境界: ある span が WRAP なしで閉じ、1 行以上欠落したのち本文を伴って再出現する行。閉塞直後の欠落 0 行の即再開は同一マスのセル内折返しであり境界にしない。
  - (b) 細分境界: 閉じて欠落した親 span の内側座標に、new span が本文を伴って出現する行（選択欄の細分等）。
* 可視行数は max 可視行番号 + 1。行ヘッダ・空行を伴わない band 宣言行群は署名が同一で本文のみの行が境界を生むまで単一可視行へ畳まれる（1 年次=1 行）。

### 16.4 レーン unit と継ぎ手連結

* 同一 span を band 内のレーンとして追跡する。直前の欠落行数が 0 の間は同一 unit へ継続連結し（閉塞直後の即再開を含む）、欠落 1 行以上の後の出現は新 unit とする。
* unit への本文追記は次の継ぎ手で連結する: 数字列は前置き半角空白、半角英数 printable 列は前後に半角空白を添える、単一文字は直接連結（縦流れの文字）、それ以外（複数文字）は [FlowPart.LineBreak]（`<br/>`）。空白のみで本文が無いマス（罫断片・斜線欄）は連結へ寄与しない。
* 可視行の出力にはその可視行で unit を開始したマスだけを左辺昇順に立てる（空マスを含む）。tall マスの rowspan は band 再構成側で「unit が跨ぐ可視行数」として確定し、buildTable の欠落槽走査へ強制 span として引き渡す。従来走査は band 外の行（列番号 footer 等）を跨いで over-span を算出し、band 内のみが正当な tall 深さの正解と一致しなかった。

### 16.5 射影と受入

* 合成契約テストは `RuleFlowVisualGridTest`（可視行 3・tall rowspan・細分・集計・幽霊行禁止・保存則。『銀河鉄道の夜』フィクスチャ）に登記する。
* 時間割様式実文書（縦書き band 3・可視行 1/3/3）: `<tr>` 57→9、gold（手修正 XHTML）tbody 7 行と colspan/rowspan 構造 100% 一致、全文字多重集合保存。罫線表様式文書は出力差分ゼロ。

## 17. 行ヘッダ付き縦書き band と細分列番号表頭・幻影空列（2026-10-01 観測・追補確定）

本節は §13.2 の継続判定・§15 の表頭取り込み・§3.6 の欠落槽補間を補完する。PDF グリッドオラクルで観測・確定した（実測 band 行は全行が行ヘッダ `w4=0x008f` を伴い、§16 の行ヘッダ無し band とは別経路（§13.2 はしご）で畳まれる版面が存在する）。

### 17.1 living 継続の維持則（白紙 WRAP-open 埋め立て行）

* §13.2 の openContinued（living）状態は本文+WRAP-open マスで**付与**される（従来契約）。
* 本文が空白で WRAP-open マス만が残る行（縦流れの埋め立て白紙行）は living を**殺さない**: 先行が living なら維持する。ただし living でない行から复活はしない（空白行から継続が始まらない）。
* 本文を伴う閉塞（WRAP なし）マスが 1 つでもある行では living を停止する（§15B 字下げ継続が拾う）。
* これにより縦流れの途中に白紙埋め立て行を挟んだ集中行（単位数等）が同一論理行へ連結される。

### 17.2 細分列番号表頭（digitHeaderLike）の構造的 Adopt

* 行ヘッダ行で表が開く際、pending の表頭行が本文行とグリッド左辺を共有しなくても、その行が**多数（8 以上）の細分マス**で構成され、非数字本文マスが 2 以下（斜め罫・「学年/時間」型の表冠ラベル等）なら、細分列番号ヘッダとして表頭行に Adopt する。
* 段落らしき行（単一広幅スパン・数字本文ゼロ）は該当せず、従来どおり段落退避で保存則 §2.2 を維持する。

### 17.3 幻影端空列の除去

* グリッドの先頭または末尾の座標について、**全行**がその左辺のマスを宣言し、その列の全マスが空白で、かつマス幅が細幅（≤8）のとき、罫表外側の残り物幻影列として列ごと除去する（byte 級 signature: 実測で列番号ヘッダを含む全行が細幅端列を空白で宣言し続ける余白条パターン）。
* 意図的な空欄（記入欄・斜め罫・§3.6 の欠落槽補間）は、非全行宣言・広幅・本文ありで不発となり温存される（§T3-1/§3.6 契約フィクスチャで担保）。
* 除去した先頭マス数分、rowspan 強制指定（band preSpans）とブロック span（blockSpans）の cellIndex をシフトして整合させる。空白列の除去のため保存則 §2.2 は不変。

### 17.4 射影と受入

* 合成契約テストは `RuleFlowHeaderedBandTest`（細分列番号表頭の Adopt・行ヘッダ付き band の単一行化＋集中数字連結・埋め立て白紙行の living 維持・幻影端列除去・保存則。『銀河鉄道の夜』フィクスチャ）に登記する。
* 時割選択様式実文書: 表頭脱落と段落転落の解消（列番号行 1 行が表頭に復位）、行毎の可視行化（集中数字が同一マスへ連結）、左右幻影空列の除去。オラクル正解グリッド 5 行×32 列と行数一致。従来対象文書（時間割様式・罫線表様式）は出力バイト一致を維持。

## 19. 語6 閉塞系（bit0）本文マスの進行を行境界とする（2026-10-01 観測・追補確定）

§14 mergeConflict の完結判定を補完する。実測（監修様式・同一グリッド連枠）では
科目名マスの語6=0x0003（完結細身）が毎行新本文で進行し、マークマス（語6=0x0001）は
列位置が行毎にずれて空欄対となるため、従来の厳密一致（語6==0x0001）では行境界を
検出できず、複数実行が 1 論理行へ過剰統合されていた。

* 判別: 標準マス（語6=0x00ff）を明示的に除外し、語6 の bit0 が立つ閉塞系マス
  （0x0001=完結・0x0003=完結細身等）の新本文が、同一 span の閉塞（WRAP-open 非）
  済本文マスへ進行したら行境界とする。
* 標準マス除外により、全マス 0x00ff の時割選択様式（§17）および WRAP-open ラベル
  レーンは不発で、従来の縦流れ連結動作を維持する。
* 合成契約テスト `RuleFlowClosedTextRowBoundaryTest` に登記する（同一グリッド 3 実行の
  科目進行で行が割れること・ラベル縦流れ連結と保存則）。対象実文書（監修様式）では
  過剰統合が解消し可視行 80→88、科目名は各行独立。既存様式（時間割・選択・罫線表）は
  出力バイト一致を維持。

## 20. jsreadermi 参照リーダーの罫・装飾マップ（2026-10-01 観察; バイナリ追補）

本追補は、Sun が無償配布した Ichitaro インポートフィルター（jsreadermi.dll、RFC 0002、ハッシュ一致確認済み）における動作の観察結果を仕様として登録する。コードの転載は行わず、観測された対応関係（コード→文字列値）の事実のみを記録する。目的は §4 のインライン罫スタイル語彙の定量的な裏付けと、§6/§7.2-3 の LayoutBox 再帰解析に必要なセル罫属性モデルの確定である。解析成果はスクラッチパッドでの逆アセンブルにより得たものであり、アドレスは証跡アンカーとして列挙している。

**証拠レベル規約。** 本リーダーは相互運用性の実現のために Sun が独自に実装したものであり、その内部構造は JTD フォーマットの正典（正典的規定）ではない。よって主張にレベルを付す: **[L1]** = バイナリで観察された挙動（Sun の参照リーダー — RAM モデルと SAX 射影 — に関する事実）、**[L2]** = [L1] から導いた JTD の on-disk エンコーディングに関する推論で、コーパスでのバイトレベル検証待ち。[L1] の事実はそれ自体では on-disk のレイアウトを保証しない。

**証拠系列規約（2026-10-02）。** 2 つの証拠系列は判定完了まで分離して保持する: **[Sun-Ichitaro8]**（§20.1〜§20.7。フィルターの一太郎 8/9/10/11 対応は owner 提供的知見であり、oxt の `description.xml` にバージョン範囲の記載はない）および **[corpus-2026]**（§20.8。一太郎 2026 で作成した probe のバイト差分 ground truth）。§20.7 の文法が 2026 native バイトに存在すると主張すること、または §20.8 の record を §20.7 の辺 slot に bind することは、§20.7 の判定実験（一太郎 8/9/10 世代の controlled corpus、spool 捕捉）完了まで行わない。フィルター対象世代と 2026 の約 20 年の native バージョン差は、未判定の結合を危険なものとする。

### 20.1 ストリームオープン・ロールマップ

フィルターは入力ストリームを名前で開き、専用ローダーでモデルへロードする。検出された対応関係は次のとおり。

| ストリーム | 役割（観察） |
| :--- | :--- |
| `DocumentText` | 本文。専用テキストローダー（`0x10038280` 経由） |
| `LayoutBoxText` / `Header` / `PageLayoutStyleHeader` | 本文系ストリーム（同一ローダー系 `0x10039150`） |
| `LayoutBox` / `Figure` / `FDMIndex` / `FDMVector` | 構造オブジェクト系ローダー（`0x1003cde0`） |
| `FigureData` / `main_data` | 生データローダー（`0x1003cea0` 系、埋め込み Press 系コンテンツと整合、RFC 0011 参照） |
| `EmbedItems` | 埋め込みアイテム列挙（3 箇所で参照） |

併せて、入力は一時ファイルへスプールされる（`GetTempPathA`/`GetTempFileNameA` と `fopen`/`fread`/`fclose`/`remove` の使用痕跡）。バイナリ内の文字列データは ANSI/Shift-JIS 主体で、UTF-16 の語彙リテラルは存在しない（フォント名断片のみ）。

ローダーの二分岐自体が構造的観察である [L1]: 本文系ストリーム（`DocumentText`、`LayoutBoxText`、`Header`、`PageLayoutStyleHeader`）はテキストローダー系へ、`LayoutBox`/`Figure`/`FDM*` は別系統の構造オブジェクトローダーへ通っている。参照実装の立場から、罫線を内包する本文と構造化 LayoutBox オブジェクトが性質の異なるものであるという §6 の立場を独立に支持する。これは Sun の設計に関する事実であり、それ自体がフォーマットの主張となるものではない [L2]。

### 20.2 セル辺の罫線記述子（4 辺 × 32bit）

参照リーダーのセルモデルは、1 セルあたり 4 つの辺指定子（左 `+0x04`、右 `+0x0C`、上 `+0x14`、下 `+0x1C`。RAM 上のセルレコードは stride 0x20）を持つ — これらはすべて **[L1]**、すなわち Sun のパース後の RAM レイアウトであり、`/LayoutBox` の on-disk のバイト列についての記述はまだではない。各指定子は 32bit で、最上位バイトが罫スタイルコード、下位 24bit が RGB 色である。射影規約は次のとおり [L1]:

- スタイルコード `0` → `fo:border-<edge>` = `"none"`
- 0 以外 → `fo:border-<edge>` = `"<width>cm <style> #<RRGGBB>"`（色は BGR→RGB へ正規化後に整形）
- コード `4`（二重）の場合に限り `style:border-line-width-<edge>` = `"0.002cm 0.088cm 0.002cm"`（outer inner outer）を併発

スタイルコード対応表（`0x10034930` の分岐とジャンプテーブル `0x10034c8e` で二重確認）:

| コード | 太さ | 様式 |
| :--- | :--- | :--- |
| `0x01` | 0.035cm | solid |
| `0x02` | 0.088cm | solid |
| `0x03` | 0.002cm | solid |
| `0x04` | 0.092cm | double |

セルスタイルは `<style:style style:name="cell%d" style:family="table-cell">` として自動生成され、`table:style-name` 参照でセルへ紐付く。列幅の算出は 16bit 語にスケール除算（× [rec+0xC] >> 1）を施す形式で、RFC 0006 §13.2 の語とスケールの併記と整合する。

### 20.3 枠・装飾のスタイル語彙

テキスト枠の枠罫は（線種）×（太さ）の総合格子上で、`single`/`double`/`triple` に 0.001cm〜0.17cm の 13 段階幅、破線パラメータ {450, 900, 1200, 1350, 1500, 1800} を組み合わせた CSS 値（CDATA 内）として整形される（分岐ディスパッチには `0x1e`・`0x16`・`0xd3` 等のコード帯が観測される）。装飾（下線・取り消し線）語彙として `none`、`single-line`、`thick-line`、`double-line`、`small-wave`、`double-wave`、`bold-wave`、`bold-dotted`、`bold-dash`、`bold-long-dash`、`bold-dot-dash`、`bold-dot-dot-dash`、`wave`、`dotted`、`dash`、`long-dash`、`dot-dash`、`dot-dot-dash`、`double` 等が実在し、一太郎の波浪系下線の豊富さを裏付ける（§7.2-4 の入力）。

### 20.4 生成地点 — レコード構築パイプライン

セルレコードの出自に関する L1 証拠を所在地まで特定した。2 つのビルダー関数（`0x1000eec0` と `0x10017268`）はサイズ `0x51C` バイトの単位レコード（スタックフレーム `lea edi, [ebp-0x51C]`）を組み立て、part の存在フラグをレコード先頭オフセット `0x00` の WORD にパックし（bit0/bit1/bit2 のゲーティング）、オフセット `0x1E` に 16bit の罫コードを配置し、1 レコードパスでコード正規化器（`0x1001fdb0`）を **4 回** 呼ぶ — 辺ごとのパイプラインである [L1]。

正規化器は `0x10056770` のバイトテーブルで WORD コードを解決する（`0x00`〜`0x10`。`0x0000`/`0xFFFF` はまず `1` へ正規化）。観測された 17 エントリのエイリアステーブルは多対一で {0,1,2,3,4} の 5 分類へ畳まれる（例: 原コード `0x01`→3、`0x02`→1、`0x03`→2、`0x07`→4、`0x08`→4、`0x0F`→4、`0x10`→2）。Sun が最終的に射影した 4 種の表示スタイルより豊かな原罫コード体系を認識していたことがわかる [L1]。隣接するポインタテーブル（`0x100567A8`）は正規化 index を装飾名文字列（`single`、`double`、`dotted`、`*-wave` 等）へ対応付け、§20.3 を裏付ける。

帰結 [L2、詳細化]: `/LayoutBox`（および兄弟）の on-disk 単位レコードは、(a) 存在フラグビット、(b) 辺ごとの collapse 前の 16bit 原罫コード、(c) 罫色ワード を持つべきである。RAM で観察した `0x51C`/`0x20` の stride はファイルレコード stride の候補であって、確定ではない。

### 20.5 RFC0013 との突合と帰結

1. §4.2 に対し [L1→L2 待]: `0x22`（細罫）・`0x1c`（太罫）には「細 = solid 0.035cm、太 = solid 0.088cm」という定量的*参照*錨が得られる。ただしこれは Sun の選んだ量子化であり、JTD の正典値ではない。符号化も別層（インラインヘッダー語 vs. オブジェクトモデル指定子）。コード意味の同一性はレンダリング出力とのコーパス検証待ち。
2. §6 に対し [L1]: Sun の RAM モデルではセル罫属性は 4 辺独立の指定子であり、ローダーは本文系テキストと構造オブジェクトに二分される。したがって §7.2-3 の再帰解析での §4.2 フッターコードの同じ 4 辺モデルへの正規化は、Sun の方式に学んだ*設計目標*であって、フォーマットが保証する形ではない。
3. コーパス検証タスク [L2]: `/LayoutBox` のセルエントリでのバイトレベル確認 — (i) 1 セルあたり 4 つの罫フィールド（コード + 色）、(ii) §20.4 のエイリアステーブル領域（`0x00`〜`0x10`）と整合する 16bit 原コード、(iii) 宣言済みレコードオフセットでの存在フラグ WORD。不一致の場合はフォーマット構造のせいにするのではなく、Sun 内部の正規化（RAM stride `0x20`/`0x51C` は実装アーティファクト）として切り分ける。
4. §5 に対し: Sun の幅の量子化は `data-rule` の太さトークン（細→0.035、太→0.088、二重→0.092）へ展開できるが、参考語彙に留める。規範的トークン定義はコーパス由来の証拠を待つ。
5. 答え合わせの機会（§7.2 の方向）: 生成地点（罫線を担う入力 → 4 辺正規化器 → `0x51C` レコードビルダー → セル・エミッタ連鎖）が所在地特定済みなので、我々の Kotlin 実装（500 行超）の `RuleFlowParser`/`RuleFlowAssembler` のヒューリスティックを Sun の正規化判断と一項目ずつ照合する段階に入れる — 参照解答として、採否はコーパス証拠で決める。

### 20.6 辺別罫表のストリームバインディング（直接観察への昇格）

JTD のバイト列と 4 辺セルモデルの間の隔たりが、具体的な連鎖として絞り込まれた。

* リーダーはコンテナストレージから `PageLayoutStyle`（`this+0x225c` に保存）と `TextLayoutStyle`（`this+0x2258`）を開く [L1]。両ストリーム名はすでに RFC 0002 のインベントリに掲載済みである。
* 開かれた各ストリームは item selector `0x10039920(stream, 1)` と `0x10039920(stream, 2)` 経由で address される — スタイル系ストリームは **indexed-element container** として扱われる。これによりストリームあたりの sub-item 構造が確定する [L1]。
* パースループ（`0x100169f8` と兄弟）は live item cursor から count WORD を読み、stride `0x584` のレコード配列を確保する。後続のイテレーションは小単位フィールドのカーソル読みと `[this+0x2444] + i*0x584 + off` への store を交互に繰り返す [L1]。1 レコードパスの call census は WORD カーソル（`0x1003a5b0`）13 回に DWORD カーソル（`0x3a600`）と解放 helper の呼び出しが加わる構成で、**`0x584` ブロックの一括読みは存在しない** — ループは byte cursor（`0x1003a540`、1 バイトずつの primitive）をフィールドごとに消費する。
* **エンディアン**: WORD cursor `0x1003a5b0` は byte cursor 経由でちょうど 2 バイトを読み、バイトスワップ（下位→上位、上位→下位）してから返す。`0x3a600` は同じことを 4 バイトで行う — スタイル系テーブルストリームは **big-endian** である [L1-direct]。このエンディアンはリーダー自身の I/O プリミティブが実演するものであり、RFC 0006 で `/DocumentText` について確立済みの big-endian 語読みを独立に裏付ける。
* ビルダー A（`0x1000eec0`）/ B（`0x10017268`）はこれらのレコードを消費し、辺別の WORD が `0x1001fdb0` × 4（§20.4）→ エイリアステーブル → 正規化辺コード → cell emitter へ流れ込む [L1]。

証拠状態の更新: 1 バイトずつのカーソルプリミティブ、big-endian WORD/DWORD エンコーディング、count WORD ヘッダー、sub-item address 方式は **直接観察 [L1-direct]** — カーソルの挙動が file ダンプより前にエンコーディングと読みフィールドを固定するからである。stride `0x584`/`0x51C` は **RAM スロット stride [L1-RAM]** であり、on-disk のレコード stride と一致するか否かは依然 **[L2]** のまま（ブロック読みは観測されておらず、ループはフィールド単位）。未解決 **[L2]** として、JTD コンテナ内の `TextLayoutStyle`/`PageLayoutStyle` の正確なバイトオフセットとセクション境界が残る。コーパスタスク: サンプルで両ストリームの所在を特定し、観測されたフィールド順序（count WORD ヘッダー → BE WORD 13 回 + DWORD の並び）をリプレイして 1 レコードを歩み、消費バイト数が RAM stride 候補と一致するかを検証すること。

### 20.7 罫レコード1件のフィールド順序（Sun リーダーレベル [L1-Sun-reader]、stride 仮説の排除）

parse 側の数え上げにより、固定 stride 仮説は tag 駆動＋presence bitmap 符号化に置き換わった。観測された層は 2 つで、いずれも on-disk の `0x584`/`0x51C` を否定する。

**層1 — `LayoutBox` stream object**（walker `0x10011970`、`0x1003cde0(storage, "LayoutBox")` で open）[L1]:

* 8 バイトのヘッダーを `0x1003d330(obj, 8, 0)` で seek スキップし、本体は `remain = [obj+0x10] − 8` で走査する。
* エントリ: TAG = BE WORD（`0x1003a6c0`）。TAG == `0x6668` の場合 LEN = BE DWORD（`0x1003a710`）、そうでなければ LEN = BE WORD。payload は LEN バイトで、構造消費されない限り `0x1003a680` により 1 バイトずつ drain される。
* TAG `0x201`（LEN の bookkeeping は観測上 `== 8`）: payload = BE DWORD × 2 → `[this+0x27f0 + idx*8]` へ順次 store（32 ビット値 2 つ。消費側の役割は TBD [L2]）。
* 1 エントリの bookkeeping: TAG(2) + LEN(2 または 4) + payload。**この層に固定レコード stride は存在しない [L1]** — `0x584`/`0x51C` は RAM 専有のレイアウトへ降格し、§20.6 の留保が確定する。

**層2 — `TextLayoutStyle` の style-table items**（`0x584` RAM 配列への 3 パス fill、`0x100169f8`）[L1]:

* Pass R（item #2 cursor）: WORD `N` → alloc `N×0x584` [L1-RAM]。レコード *i* ごと: WORD `M_i` → rec+`0x538`、続いて `M_i`× BE WORD → rec+`0x540 + 2j`。レコードあたりの on-disk 消費は `2 + 2·M_i` バイト。
* Pass K（item #1 cursor）: WORD `K`。グループごと: WORD `L`、`L`× WORD の key list を scratch へ、BE DWORD の marker。key list とテール配列がバイト一致（`repe cmpsb`、`L·2` バイト）した全レコードの `rec+0x53c` へ marker を書き込む。
* Pass P（marker ごと）: `0x10039920(TextLayoutStyle, marker)` で sub-item を取得。item は BE WORD マジック **`0x5555`** で始まり、WORD の skip count + skip× WORD の drain、続いて WORD の**値幅記述子** `A`、その後 **property opcode loop**: opcode WORD、`0xFFFF` = item 終了。dispatch は jump table `0x1001793a` による `0x5001`〜`0x500B`:
  * `0x5001`/`0x5009` → handler `0x10017a50`（block = `this+0x26f4`、`0x58C` alloc の base）: 最初に BYTE の**presence bitmap**（block+`0x00` に store）。bitmap の下位 8 ビットが aligned slot `+0x01/+0x02/+0x04/+0x06/+0x08/+0x0A/+0x0C` の presence を gate する（BYTE か WORD かは jump table `0x10017e49` で判定）。続いて BE byte → `+0x10`、`+0x11`。その後 **4 つの辺 slot `+0x14/+0x18/+0x1c/+0x20`** — それぞれ `A == 0x4003` のとき **BE WORD**、そうでないとき BE DWORD で読まれる [L1]。続いて 4 バイト → `+0x24..+0x27`、2 バイト → `+0x28/+0x29`。slot `+0x2c` は `A == 0x400a` のとき BE DWORD、そうでないとき BE WORD。
  * `0x5003` → BYTE 配列を `this+0x26fc` へ（loop count は opcode word から取り、`0xfa` に clamp）。`0x500A` → BE DWORD 配列を `this+0x26f8` へ（count = opcode word `>> 2`、`0xfa` に clamp — 容量は builder slice `0x3E8` バイトと正確に一致、§20.4）。
  * `0x5004`/`0x5005`/`0x5006` → `this+0x2700`/`+0x2704`/`+0x2708` への sub-parser。`0x500B` → scratch。`0x5002`/`0x5007`/`0x5008` → skip-drain。
* §20.4 との接続: この 4 辺 slot が `0x1001fdb0` × 4 正規化入力の生産者である。builder が読む「`+0x1e` の WORD code」は DWORD 符号化された `+0x1c` slot の上位ハーフに位置する — 矛盾ではなく一致である。

証拠状態: 上記の tag/opcode/bitmap による**フィールド順序は [L1]**（consumption 順序は reader により固定）。辺の同一性（`+0x14..+0x20` のどれが上/右/下/左か）、slot 値の意味領域（§20.2 のコード表）、マジック `0x5555`/`0x6668`/`0x201` の意味、`this+0x27f0` の消費側の役割はすべて **[L2]**。コーパスタスクの精緻化: サンプルで `TextLayoutStyle` item を所在特定し、マジック `0x5555` を確認したうえで property opcode loop を歩き、4 辺の値が同一文書に対する Sun filter の `fo:border-*` 出力と一致するかを検証すること。

**スコープと version confound（2026-10-02、矩形罫 probe コーパス）。** 一太郎 2026 を用い、単一矩形の罫線文書 6 本（base、片辺太線: left/top/right/bottom、および四周別色 1 本）を作成し、native CFBF コンテナ（directory stream: `DocumentText`、`DocumentViewStyles`、`TextLayoutStyle`、`LineMark`、`PageMark` 他）から展開して走査した。観察結果として、native ファイルのいかなる stream にもマジック `0x5555`、opcode 空間 `0x5001`〜`0x500B`、および記述子 `0x4003` は存在しない。しかし、この否定結果から直ちに帰属を導くことはできない — `jsreadermi` filter は**一太郎 8/9/10/11 世代**を対象としており（owner 提供的知見）、本コーパスは一太郎 2026 の native であるため、§20.7 の文法に関しては少なくとも 2 つの仮説が生存する: **H1（spool 層仮説）** — native 入力を消費する過程で Sun リーダーが生成する自前の stream-object/内部表現であるとする説。**H2（旧 native dialect 仮説）** — 一太郎 8 時点の native JTD on-disk エンコーディングであり、後続の native 版で符号化が変更されたとする説。したがって、本節の文法に関する主張はすべてリーダー挙動の観察 **[L1-Sun-reader]** であり、native バイトへの帰属は **[L2-version-confounded]** とする。世代をまたいで維持されるのは幾何の連続性である — 同一寸法で作成した矩形は、style 語彙が分岐しても、比較可能な addressable な geometry 差分を残す。probe コーパスの native バイト観察は証拠系列 **§20.8 [corpus-2026]** として別途登録し、本節の事実はそこに紐付けない。特に §4.2 のコード語彙（`0x1c`/`0x22`）は**本 2026 コーパスでは再現せず**、version/layer を含む帰属は未確定である — どちらにも断定しない。判定実験: (a) **一太郎 8/9/10 世代で controlled corpus を作成**（v10 と同世代の Lite 2 が利用可能。辺の太さという位相的 ground truth が取れていればよく、ピクセル単位の幾何精度は不要）し、native stream を走査して magic/opcode/descriptor を確認する — 存在すれば H2 を直接支持し（リーダーは native を直接読んでいる）、不在なら H1 を支持する、(b) **Sun 変換中の reader spool を filesystem monitor で捕捉**し、spool バイトと 2026 native stream を比較する。

### 20.9 Lite 2（8/9 世代互換）probe — 系列 `[corpus-legacy]` と判定更新

同一の 6 構成を一太郎 Lite 2（v10 と同時期リリース、互換性は 8/9 近し — owner 提供的知見）で作成し、native CFBF コンテナから展開した。観察は次のとおり。

* **判定データ点**: Lite 2 ファイルのどの stream にも `0x5555`・`0x5001`〜`0x500B`・`0x4003` は存在しない（両エンディ配置を確認）。2026 コーパスに続き第二の否定となり、仮説 **H2（旧 native dialect）は真の一太郎 8/9 オリジナルへ缩小**（まだ反証はしていない — Lite 2 と 8/9 のバイト同一性は保証されない）。**H1（リーダー側表現）が優勢だが未証明**。§20.7 への結合は登録しない。
* **コンテナ方言差**: Lite 2 には `TextLayoutStyle` ストリーム自体が存在しない（2026 にはある）。ストリーム集合は世代で異なる [corpus-legacy]。
* **レコード framing の連続性**: `DocumentText` は `NN 00 00 31` レコードの安定台帳であり、payload ラベルは UTF-16LE で作者メタデータ（`作成`、`作成時間`、`前回更新`、`ページ数`、`会社` 等）に復号される。tag はファイル間で安定し、編集はレコードを**追記**する（太縦変数は tag `0x07` と `0x16` を追加、別色変数は 4 レコード追加、ファイル増分 `+0x30C`）[corpus-legacy]。
* **交差汚染の同定**: `DocumentText`（`0x380`・`0x588`）と `DocumentViewStyles`（`0x380`）の対 4 バイト窓は、どの辺が変わっても変化し、1 次元だけ意味編集が異なるファイル間でも異なる — **保存毎の checksum/stamp 窓**と整合する。`52 dd 01` stamp 族は両世代に出現する。raw 赤（`ff 00 00`）は別色ファイルで 1 箇所（`DocumentText+0x949`）所在特定済み。青/緑/黄は raw RGB として未発見 — palette/index 混合符号化の疑い、意味は保留。
* **手法の転換 — 決定 probe**: ファイル間差分は stamp と汚染で飽和した。制御された 2 probe で意味とノイズを分離する。(P1) 無編集で同一ファイルを**ダブルセーブ** — 変わるバイトが stamp、残りがノイズ校正。(P2) **単一ファイル内に二つの矩形**（片方を太縦辺、もう片方を四周細）— 辺↔レコードの bind がクロスファイルノイズゼロの単一文件内で完結する。主地探测器は P2 であり、ピクセル精度の位置指定は不要。

parser 側 bind（parser events → `RuleFlowAssembler`）は `[corpus-2026]`・`[corpus-legacy]` とも未充填のまま。

**P2 単一ファイル probe（二矩形配置文書、[corpus-legacy]）— 観察登記。** `DocumentText` 末尾に ASCII 番号 `'1'..'7'` のユニット台帳が新設される。各ユニットは subfield `NN 04/05/06/07` を持つ。sub04 は bit-`0x80` フラグ付き geometry word（§4.2 の壁語彙 `b_0=80` と整合）、sub05/sub07 はユニット 2〜6 で同一、**sub06 はユニットごとに異なる**（`06 03 00 09 01 07 08` / `07 03 00 0b 01 00 07 d0` / `06 03 00 0a 00 …` / `06 03 00 0a 03 …` ×2 / `05 03 00 08 …`）— 帯単位の罫台帳の候補。bind を阻む未決事項が 2 つ: (i) ユニット 2〜6 の sub04 幾何が同一であり、非対称な 2 矩形がこの台帳内ではまだ識別できない（この層に bbox 範囲が 1 本しか記録されていないか、2 本目の範囲が他所にある）、(ii) 作成 ground truth（どの矩形にどの太辺/幅/色を置いたか）は owner の確認待ち。`0x1c`/`0x22` は本ファイルでも再現せず。

### 20.10 ダブルセーブによる校正 — 改訂（権威再測定。以前の指紋系の主張は撤回）

権威 reader（POIFS・production 等価。§20.11 勘誤）による無編集再保存ペアの再測定:

* **内容層は保存を跨いでバイト安定**: `DocumentText`、`Font`、`Header`、`LineMark`、`PageMark`、`PaperMark`、`DocumentEditStyles` は original と resave でバイト一致。以前の「全 stream の `+0x14`/`+0x20` 保存カウンタ」「`DocumentText` の指紋移動」の主張は**撤回** — どちらも抽出器アーティファクトだった。

* コンテナは物理セクタ配置のみ異なり、POIFS 経由の論理ストリームは安定集合について同一。
* 方法論の恒久注記: bind は引き続き parser の決定論的走査経由 — ただし根拠は世代間のアドレスドリフトと揮発メタデータ層であり、保存毎の内容層 churn ではない。
* フォントレコード族 `03 02 01`（+ `12 00` + "Times New Roman"）の同定は有効のまま。
* §20.9 の台帳／一意性 bind（`d0`/`0b`）は無効: 台帳自体が抽出アーティファクトだった（§20.11）。

### 20.11 壁様式エントリと `WallRule` イベント（P2 解読、[corpus-legacy]、2026-10-02）

**エクストラクタ勘誤（§20.9/§20.10 に適用）。** 当該フェーズで使った作業用 CFBF 抽出器に FAT チェーン順序の欠陥があった。そこで報告したバイトダンプ・アドレス・「ASCII ユニット台帳」は抽出アーティファクトであり撤回する。権威あるリーダーに差し替えた結果、P2 probe とその無編集再保存の `/DocumentText` はパイプライン traversal 経由で**バイト一致**（コンテナは物理セクタ配置のみ異なる）。両世代とも同一の §4 語彙 `SsmgV.01` ヘッダが現れる。「保存非再現の指紋／台帳再符号化」の主張は差し替え済みで、保存往復の振る舞いは **parser レベルの不変性**として `CorpusRuledBoxGroundTruthRailTest`（oracle-1）で確定した。

**壁様式文法（末尾様式域・実測）** — エントリ形式 `[id] FE [sub1] [sub2] [style WORD] …`:

| エントリ | 意味 | 根拠（[corpus-legacy]） |
|---|---|---|
| `FE 02 02` + 様式語 `0x0003` | 太縦壁 | 太左 probe・太右 probe・P2 狭矩形 |
| `FE 03 02` + 様式語 `0x0003` | 太横壁 | 太上 probe・太下 probe |
| `FE 02 02` + 様式語 `0x0000` | 細縦壁 | 太 probe の後続エントリ |
| `FE 01 02` / `FE 10 04` / `FE 0F 04` | 予約（未確定） | 反復 interior エントリ・color probe の色族 |

全辺細の文書は `FE 02/03` エントリを**持たない** — 細は既定で太のみ宣言される。先頭の id バイトは同一辺の probe 間でも壁の配置により変動するため、id→辺の解読は次段階に留保し、本節のレールは方向・太さ・本数を確定する。

**イベント契約。** `FlowEvent.WallRule(orientation, weight)` — module-internal、`FlowBlock` を作らず XHTML 出力是不変。レール `rulebox.rail` は保存往復ペアの各ファイルに対し次を検証する: oracle-1 — 無編集再保存を跨いで payload／イベント／ブロックが一致（保存再符号化に対する意味的不変性であり、正しさの証明ではない）。oracle-2 — 太縦ちょうど 1 本・太横 0 本。これは owner 確認済み ground truth「先出の狭い矩形の左辺のみ太・他の全辺と広い矩形は細」のセマンティック射影である。

**結合禁止。** 以上は §20.7 の Sun-reader 語彙には一切触れない。[Sun-Ichitaro8] は分離保持のまま結合しない。

**未決事項（既存）。** `flowstruct` レールの T3-1 検査は現在、セル内 `<br>` 30 個の残存で失敗する。これは §20.11 の変更より前から存在し（変更を戻しても再現）、§13.2 縦継続セルの `LineBreak` 継ぎ目との既知の干渉が原因とみられる。受入文言の §13.2 との整合裁定は別トラックで追う。
### 20.12 測定規律（規範的、2026-10-02）

**ネイティブバイトの観測は、production 等価の POIFS traversal 経由か、独立した相互検証を経たうえでないと、コーパス証拠に昇格してはならない。**

根拠（§20.11 の事件 —「測定器が現象を作った」）: FAT チェーン順序の欠陥のある作業用 CFBF 抽出器が、production パイプラインがバイト安定で読むストリームに、見かけの保存毎再配置・幻影台帳・偽指紋ノイズを捏造した。SELF 検証ゲートがあったので仮説は積み上がる前に自壊したが、規律として規範化する:

1. 本 RFC に登記するバイトアドレス・差分・個数は、(a) production parser 走査（`JtdContainerReader` 経由の POIFS）または (b) 第二の独立 reader から再導出可能でなければならない。
2. 再導出できないものは、測定器の注記を明示した scratch 観察として記録し、コーパス証拠としては記録しない。
3. 意味レールは測定段階自身の生バイト指紋に依存してはならない（§20.11 の oracle-1／oracle-2 分離がこのパターンとして有効）。

### 21. T3-1 レールの再同期 — セル単位 oracle 同一性（2026-10-02 裁定。登記のみ・挙動変更なし）

### 22. O2 census — native 構造から導出不能な継ぎ目意図（2026-10-02。登記のみ・挙動変更なし）

本追補の本体: §21 の O2 継ぎ目残差 ±1 は**production 規則の欠陥ではない**と裁定した。縦継続の単一 CJK 文字行における継ぎ目の採否は oracle 専用の筆記意図であり、現時点の native fingerprint からは**導出不可能**である。大家の意図を推測させる判別規則を `joinVerticalRun` に追加してはならない。

census 手法（秘匿安全）: production パイプライン（payload→RuleFlowParser→RuleFlowAssembler）をリポジトリ外の friend モジュールアクセスで端到端実行し、完全 SAX 出力と自己照合（cells=128・セル内継ぎ目総数 175・セル単位一致 true）。観測は整数・span 座標・語値・文字クラスヒストグラムのみ。

固定点:

1. **旧仮説の棄却**: §13.2 統合 vs §14.2 閉塞の判別は O2 を説明しない。本中書の span 宣言 844 語は全文 word-6 = `0x00ff`（word-7 = `0x0000`）。§14 R2 閉塞衝突・§19 完結系 bit0・§14 R4 下方アンカー（word-7=`0x0002`）はいずれもこの文書で未発火。閉塞抑制は suppressor ではない。
2. **word-6 census**: 対象 population（span 宣言全集）844/844 = `0x00ff`（標準・継続）。完結系の値はゼロ。
3. **parser 側は既存 §16v2 `joinVerticalRun` の文字クラス分岐で完全説明**: 分岐規則（全数字→半角スペース、pure-ASCII→半角スペース、`len == 1`→直結、それ以外→`LineBreak`）からの継ぎ目数予測は、整列した全出現ウィンドウで parser の実際のセル内 `LineBreak` 数と一致。−1 の 5 セル（index 44/53/54/76/81・各 −1）は単一 CJK 文字 join が `len == 1` で平坦化される位置に局在。+1 の 1 セル（index 79）は oracle 側の行融合で逆方向。
4. **oracle 側の 98/5 分岐は native 上区別不能**: 同一 native signature（`0x00ff`+WRAP 終端の縦継続宣言）のもとで、所有者再現 HTML は 128 セル中 98 セルで `<br>` なしの直結（セル内 br ゼロ）、30 セルで表示行ごとの `<br>` を保持（oracle br 総数 179）。非 `LineBreak` join の交差表: 制御群は単一 CJK join が WRAP 46＋非 WRAP 2 で、すべて br ゼロのセルに所在。差分群は WRAP 3＋非 WRAP 2 で、すべて行毎 br 保持のセルに所在。両群を分ける native 特徴は観測されなかった。

帰結: O2 は「parser 継ぎ目消失の修正待ち」から **"oracle 専用継ぎ目意図 / native 構造から導出不能"** へ再分類する。strict レール `inCellBrVectorIdentityVsOracle` は登記済み red のまま据え置く。その赤はこれで未確定の筆記意図の証拠であり、デコード欠陥の証拠ではない。本登記はレールを緑にせず、また production 変更の正当化にもならない。
